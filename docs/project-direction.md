# 选题建议与下一步

日期：2026-10-28。以下是研究后的**候选方案**，尚未确认产品方向、验证需求或开始应用实现。官方要求见 [比赛规则](hackathon-rules.md)。

## 候选方向

| 方向 | AI 的实际作用 | PayPal 的实际作用 | 取舍 |
| --- | --- | --- | --- |
| **需求变更确认与收款助手（推荐，暂名 ScopePay）** | 比较原约定与新要求，指出新增、已包含和不明确的工作，并引用依据 | 增量工作确认后开 Sandbox 发票，客户付款，核实到账状态 | 用户与流程明确；需要验证需求和分类准确性 |
| 垂直小商户的对话购物助手 | 从限定商品目录中按用户约束选商品并解释组合 | Sandbox Checkout 创建、批准及 capture 订单 | 好演示；普通聊天购物竞争多，需要具体品类和差异 |
| 自由职业者收款核对助手 | 总结已付／未付状态，建议下一步 | 查询发票、关联付款 | 较易完成，但单独参赛创新不足，可作为推荐方向的一页 |

以上可行性是基于官方接口的工程判断，尚不是实际集成或市场验证结果。

## 为什么推荐需求变更

假设目标用户为独立设计师：原约定是三张海报，客户后来又要求增加两个尺寸。用户需要判断新增工作是否已包含、是否缺少定价信息，以及如何让客户确认追加费用。

单纯“用聊天生成发票”已有明显重合：PayPal MCP 已能从自然语言创建发票；HoneyBook 也提供 AI 编辑发票条目。拟验证的差异是**对照原约定识别变化、保留来源、确认增量范围与价格**。这仍是需求假设，不能称为已发现的市场空白。来源：[PayPal MCP](https://developer.paypal.com/community/blog/openai-paypal-mcp/)、[HoneyBook 发票功能](https://help.honeybook.com/en/articles/5189729-add-customize-and-share-invoices-in-honeybook)。

通用 AI 购物也有 [PayPal Store Sync](https://developer.paypal.com/store-sync/overview)。若转向购物方案，首版使用自有小目录和标准 Checkout，避免依赖 Store Sync 的申请流程。

## 推荐的最小闭环

1. **导入约定和新需求**：先支持粘贴文本，使用匿名演示材料；单一职业、单一商户、单一币种。
2. **AI 识别范围变化**：分为已包含／新增／不明确，每项链接到输入原句；信息不足时提出澄清问题。
3. **生成可编辑的变更单**：使用用户填写的价目表，服务端计算金额；模型不能编造价格。
4. **双方确认具体版本**：自由职业者审核，客户在确认页接受；修改金额或范围后需要重新确认。
5. **PayPal Sandbox 收款**：创建 draft invoice，用户明确操作后生成付款链接，买家用独立 Sandbox 账号支付。
6. **核实状态并展示记录**：串起原约定、变更依据、确认版本、发票与支付状态。

拟议技术形态：一个 TypeScript Web 应用，配服务端 API 和持久化存储；AI 服务与部署平台选定后再补实现计划。比赛并不要求使用 MCP 或特定模型。

## 三分钟演示

| 时间 | 演示内容 |
| --- | --- |
| 0:00–0:20 | 用一个明确例子解释遗漏变更收费的问题 |
| 0:20–1:00 | 展示原约定、新消息，以及 AI 分类与引用依据 |
| 1:00–1:30 | 编辑并确认变更单；演示客户接受的版本 |
| 1:30–2:20 | 打开真实 PayPal Sandbox 付款流程并完成测试支付 |
| 2:20–2:50 | 展示经 API 核实的状态与完整记录，解释价值与边界 |

演示数据如 £60 仅为样例。完整视频控制在三分钟以内，实际录制长度以最终剪辑为准。

## 技术验证重点

| 项目 | 官方依据与我们的实现建议 |
| --- | --- |
| 发票能力 | [Invoicing API](https://developer.paypal.com/api/invoicing) 与 [Agent Toolkit](https://github.com/paypal/agent-toolkit) 提供相关操作。先验证 draft → 分享链接 → 买家支付 → 查询状态，再做完整 UI。 |
| 通知副作用 | [Send Invoice API](https://developer.paypal.com/api/invoicing/v2/invoices-send) 的收件通知默认开启。MVP 生成链接时显式关闭 `send_to_recipient` 和 `send_to_invoicer`，不配置额外收件人或未来发送日期，并在 Sandbox 验证行为。 |
| 支付状态 | [发票 webhook 文档](https://developer.paypal.com/platforms/invoicing/reference/invoicing-webhooks/) 提醒 `INVOICING.INVOICE.PAID` 可能涉及部分支付或 pending。收到事件后核对 API 最新状态、ID、币种和金额；不能仅凭模型文字、跳转页或事件名称宣称全额到账。 |
| Webhook 处理 | 按 [Webhook 文档](https://developer.paypal.com/api/webhooks/overview/) 验签；应用还需去重和处理延迟／重试。 |
| Sandbox 账号 | 使用独立买方 Personal 和卖方 Business 测试账号，密钥保留在服务端环境变量中。参见 [官方 Sandbox 入门](https://github.com/paypaldev/getting-started-with-paypal-sandbox)。当前账号、权限、实际支付流程均未验证。 |
| 商户范围 | 首版仅使用自己的单商户 Sandbox。[平台开票](https://developer.paypal.com/platforms/invoicing/integrate) 有伙伴接入要求，不能据单商户演示承诺多商户平台可上线。 |

首版暂不加入邮件连接、自动催款、退款、批量付款、托管资金、多币种或多商户接入；这些会增加权限、状态处理和演示成本。后续若需要真实通知或 live 支付，另行明确操作范围。

## 开始实现前需要确定

- 用户是否愿意选自由职业者方向，还是已有更想做的问题。
- 实际居住地与年龄是否满足规则；独立参赛还是组队；赛事是否已 Join。
- PayPal Developer / Sandbox 是否可用，AI 服务和小额开发预算如何选择；凭据不放在聊天或仓库中。
- 找 3–5 位目标用户核实是否存在漏收变更费用的情况、愿意提供什么输入、是否接受客户确认页。未经授权不联系任何人。

最先值得做的验证是：**有真实需求的三个例子 + 一次完整 Sandbox 发票支付**。若任一项不成立，先调整方向，再投入完整产品开发。
